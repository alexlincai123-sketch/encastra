## 1. What failed in rc.4

`release.yml` on the tag `v0.5.0-rc.4` (run 35871329974) rebuilt the build commit on a hosted
runner and could not reproduce the published hashes: exe same size, 70 bytes different, every PE
section equal. rc.4 stays as it is; nothing below changes it.

## 2. The 70 bytes, to the input

| | developer machine | hosted runner (`win25-vs2026` 20260907.229.1) |
|---|---|---|
| Windows SDK version | 10.0.26100.0 | 10.0.26100.0 |
| MSVC toolset / link.exe | 14.44.35207 / 14.44.35228 | 14.44.35207 / 14.44.35228 |
| `um\x64\AdvAPI32.Lib` sha256 | `a0ea53377e6de11c…` | `ecafe89a632a35b1…` |
| hint `RevertToSelf` | 0x2bb | 0x2bd |
| hint `SystemFunction036` | 0x31d | 0x31f |

- `RevertToSelf` is imported by `clipboard-win` 5.4.1 (through `arboard` 3.6.1 ←
  `encastra-builtins`); `SystemFunction036` (RtlGenRandom) by `getrandom` 0.2.17 (through
  `ring` 0.17.14 ← `rustls` 0.23 ← `ureq` 3 ← `encastra-builtins`). Both declare them with
  `#[link(name = "advapi32")]`, so `link.exe` resolves them through the SDK's import library and
  copies each short import object's hint into `IMAGE_IMPORT_BY_NAME`. Crates that use
  `windows-targets` bring their own import libraries and are not affected.
- Read directly: the hints in each machine's `AdvAPI32.Lib`
  (`scripts/verify/build_environment.py --hints`), and the same two values in the executables
  (`bb 02`/`1d 03` in the local rc.4 build at 0x905e9c/0x905eac; `bd 02`/`1f 03` in the rc.5
  candidate at 0x9063bc/0x9063cc). Same SDK version string, different file: servicing inside
  one version. `vcvarsall` selects a version, never a revision. **Pinning the SDK cannot fix it.**
- The other 68 bytes: `/Brepro` replaces the COFF timestamp, the four debug-directory stamps,
  the RSDS GUID and the type-16 payload with hashes of the image. Two different bytes anywhere
  change all of them. `/Brepro` is doing what it is for and stays.
- A wrong hint changes nothing at run time (the loader falls back to a lookup by name). The builds
  were the same program; they were not the same bytes, and no repository change can make a
  developer machine and a runner agree byte for byte.

## 3. The fix: CI builds the published bytes

- `.github/actions/windows-release-toolchain` — the one recipe (Node from `.nvmrc`, `npm ci`,
  Rust 1.98.1, pinned MSVC), no build cache, used by `candidate.yml`, `release.yml`,
  `gui-journeys.yml` and `cross-machine-reproduction.yml`.
- `candidate.yml` — copy A and copy B on two fresh hosted runners; byte comparison; copy A's
  installer installed and the chooser journeys driven through it (`-Launch -Repeat 3`);
  `build-environment.json` (toolchain, image, SDK import-library digest and hints) in each copy.
- `scripts/release_fetch.py` — puts copy A into `target/` only from a qualifying run.
- `scripts/release_provenance.py` — the single judge: `candidate.yml`, dispatched or pushed (never
  `pull_request`), exact build commit, this repository, attempt 1, every job green in every
  attempt, each artefact present once with a sha256 digest; bytes read **out of the zips**, each
  zip equal to the digest GitHub holds now; copy B = copy A; SHA256SUMS consistent.
- `release_check.py` — new `artefacts.provenance`; `reproducibility` and `gui.journeys` read copy B
  and the journeys log from the verified zips (the installed-copy hash is required, which also
  ties the installer to the published executable); `--compare` onto the tree itself is refused.
- `release_manifest.py` — names the run and its toolchain; refuses local bytes without an explicit
  `--local-build`; `--verify` checks the Signature column and `site.ts signed` against Authenticode;
  publication diffs use `--no-renames`.
- `release.yml` — the gates job verifies that the manifest publishes copy A of a qualifying run
  (`release_provenance.py --verify-manifest`, `actions: read`); the third build on a clean runner
  must reproduce it; `publish` (dispatch-only, on a tag, after build and install) re-hashes the
  verified bytes against the tag's manifest, refuses if the tag moved, never replaces a release.

Reproducibility level reached: **3** (same source + identical toolchain → byte-identical, shown by
copy A = copy B on two machines) and **4** for the published artefact once `release.yml` rebuilds it
on a third runner at the tag. Level 3 does **not** extend to a developer machine (§2).

## 4. Red team of the new gate

An independent pass found, in the first cut: P0 — the release path never consulted the candidate
run; P0 — `artefacts.provenance` trusted hashes from the local JSON; P1 — signing claims never
checked; P1 — journeys log was any file; P1 — `--compare` could point at the tree itself;
P2 — rename-blind publication diff, pull_request CI runs, re-run attempts erasing failures, tag
moving before publish, event/repository unchecked; P3 — a cache comment that was false. All fixed
above, each with a test; 21 mutants of the new guards, 21 killed. Signed-release publication path
(P3) is **DEFERRED**: there is no certificate; it fails closed today.
