# Closing B7, and what closing it uncovered — 2026-09-16

The record of the work between `v0.5.0-rc.3` and a future `0.5.0-rc.4`. rc.3 is frozen: its tag,
its commits and its artefacts are untouched, and everything here happened on `rc/rc4-closure`.

`docs/RELEASE_CANDIDATE_READINESS.md` §6 said the cross-machine difference **was** the MSVC
toolset. That was one of three causes, and fixing it is what made the other two visible.

---

## 1. The installer: it was never deterministic, and agreeing was luck

### What was believed

rc.3's two release runs built the same commit on the same hosted runner, produced a
**byte-identical executable**, and wrapped it in **two different installers**. Three builds on the
developer machine produced identical installers. The hypothesis on record was that the runner
packages without the `SetDateSave off` hook, supported by reproducing the same shape of difference
locally with `installerHooks` removed: identical `header_size` (74 008), differing `total_size`,
first differing byte at `0xce18`.

### Why that could not be concluded

`header_size` is the size of the compiled script. `SetDateSave` is an NSIS **compiler flag**, not
an instruction: it adds no line to the script, it changes two DWORDs inside each `File` the
compiler has yet to read. So `header_size` is identical whether the hook is present or not, and
the measurement does not separate the hypotheses. Measured, to be sure of it: a local bundle
**with** the hook also has `header_size` 74 008.

### What the bytes actually say

The dates live inside the compressed header, in the `EW_EXTRACTFILE` entries — `offsets[3]` and
`offsets[4]` hold a FILETIME, or `0xFFFFFFFF/0xFFFFFFFF` when the date was deliberately not
stored. Decompressing the header (solid LZMA; note the properties byte `0x5D` followed by a
dictionary size of `0x00800000` reads as a DWORD with the high bit set, so a non-solid test on that
word mistakes every solid installer for a non-solid one) and walking the entries:

| installer | extractions | no date | dated | the dated one |
|---|---|---|---|---|
| local rc.3 | 161 | 159 | **2** | 2026-09-11T01:01:18Z |
| runner run 34986561347 | 161 | 159 | **2** | 2026-09-15T15:29:08Z |
| runner run 34986561591 | 161 | 159 | **2** | 2026-09-15T15:51:48Z |

**The hook was in effect on the runner all along.** 159 of 161 carry no date in every one of them.
The two that do are `$PLUGINSDIR\modern-wizard.bmp` — MUI's welcome bitmap, packaged once for the
installer's welcome page and once for the uninstaller's, by
`Contrib\Modern UI 2\Pages\Finish.nsh:93`, from `${NSISDIR}\Contrib\Graphics\Wizard\win.bmp`.

That bitmap comes out of the NSIS installation **Tauri downloads** into
`%LOCALAPPDATA%\tauri\NSIS`. Its date is whenever that download was unpacked. On this machine
that happened once, on 2026-09-11 at 01:01:19 local — which is the timestamp in the installer, to
the second. A hosted runner downloads NSIS again for every job, so the date is the job's, and the
runner's two runs are 22 minutes apart, which is exactly the gap between their two timestamps.

The hook is inserted at `NSIS_HOOK_PREINSTALL`, which Tauri puts at the top of the Install section
— line 633 of the generated script. The welcome pages are inserted at line 165. The flag only
covers what the compiler reads after it.

**So the developer machine's three identical builds agreed because a cached file's modification
time never moved, not because the recipe made them agree.** The installer was a function of its
inputs *and* of when NSIS had last been downloaded.

### The fix, and the proof

`SetDateSave off` moved to file scope in `apps/desktop/src-tauri/nsis/hooks.nsh`; Tauri includes
that file at line 31, above the pages. The macro is kept for the main binary in case a future
Tauri moves the include.

Measured with a copy of the NSIS installation and the generated script, re-stamping every file
between compilations — which is what a runner does to itself by downloading NSIS again:

| hooks | first | second | result |
|---|---|---|---|
| rc.3's (macro only) | `18cf7805…` | `88cb06e4…` | **differ at byte 53 507** |
| file scope (this fix) | `2376cb1b…` | `2376cb1b…` | **identical** |

`scripts/verify/installer_determinism.py` makes that a gate rather than an anecdote: it packages
an existing build twice and requires the same bytes, **re-stamping Tauri's NSIS installation in
between**, because without that it would pass on the machine where the defect was invisible.
Verified through the real `tauri bundle` path, and mutation-checked — with rc.3's hooks restored
it fails at byte `0xce18`, the same offset seen between the runner's two production installers.

It now runs in `release.yml` and in the cross-machine workflow, and **passed on the runner**.

## 2. The executable: three causes, one behind the other

### 2.1 The MSVC toolset — real, and only part of it

`rustc 1.98.1` is pinned; the C toolchain under it was pinned by nothing. rustc does not carry a
linker — it asks Visual Studio and takes whatever that installation calls its default.

In September 2026 GitHub's `windows-latest` became **`win25-vs2026`**: Visual Studio Enterprise
**2026** (18.9.12120.119). Recorded by `.github/workflows/toolchain-inventory.yml`:

| toolset on the runner | cl | link |
|---|---|---|
| 14.29.30133 | 19.29.30159 | 14.29.30159 |
| **14.44.35207** | **19.44.35228** | **14.44.35228** |
| 14.51.36231 | 19.51.**36256** | 14.51.**36256** |

The developer machine has only 14.44.35207. 14.51 is the runner's default, and 36256 is exactly
the linker build rc.3's Rich header named there.

The image still carries 14.44.35207, so the release asks for it:
`vcvarsall x64 -vcvars_ver=14.44`, in `.github/actions/msvc-toolset`, which fails loudly if a
future image drops it. **Result: the two executables' Rich headers are now byte-identical** —
every record, same tool builds, same object counts.

And three megabytes still differed. Which is how the next one was found.

### 2.2 Build paths that name the machine — the largest cause, never diagnosed

rustc writes the path of every source file it compiles into the binary, for panic messages and
`#[track_caller]`. For a dependency that path is inside the Cargo registry, which lives under the
**user's home directory**:

| | build path | occurrences |
|---|---|---|
| this machine | `C:\Users\alexl\.cargo\registry` | 433 |
| hosted runner | `C:\Users\runneradmin\.cargo\registry` | 433 |

The same count and a different length, so every string after the first one shifts, and the
relocations follow. That is the three megabytes.

Cargo's `trim-paths` would say this properly and is **not stable in 1.98.1** — it does not fail
gracefully either: an unknown profile key makes the whole workspace fail to parse. So it is done
with `--remap-path-prefix` through RUSTFLAGS, composed by `scripts/verify/toolchain.py
--rustflags`, which also carries `-D warnings` along because setting RUSTFLAGS replaces it.

`toolchain.py --check-binary` looks for the giveaway **structurally** — any absolute path to
anyone's Cargo registry — so an artefact downloaded from a runner can be judged here rather than
only where it was built.

### 2.3 What is left: 70 bytes, and exactly why

Same commit (`bfb5d45`), same recipe, both machines, **identical sizes** (9 846 272):

```
Differing bytes: 70 in 9 run(s)
By class: data 2, debug 64, metadata 4
.text same · .data same · .pdata same · .rsrc same · .reloc same · .rdata DIFFERENT
```

Sixty-eight of those seventy are `/Brepro` doing its job: the COFF TimeDateStamp, four
debug-directory timestamps, the CodeView RSDS GUID and the repro payload are all hashes **of the
image**, so they differ because something else does.

The something else is **two bytes**, each larger by exactly two on the runner. They are import
hints — the index the linker copies out of an import library — for three `advapi32` symbols
(`ImpersonateAnonymousToken`, `RevertToSelf`, `SystemFunction036`).

Both machines report Windows SDK **10.0.26100.0**. The import libraries inside that same version
folder are not the same file:

| | size | sha256 |
|---|---|---|
| this machine | 178 306 | `a0ea53377e6de11c5fdc07e72af11d22d8fa613cecc6ccb1b6de43490392eadc` |
| hosted runner | 178 306 | `ecafe89a632a35b183c2129d2d8612b31a4d43a9cda78c4b2e3bc6b130ae3c6f` |

Same version, same size, different contents: two differently serviced copies of one SDK. **No
version pin can catch this**, because the version is identical.

A hint is an optimisation — the loader falls back to the name — so nothing about the program
differs. But it is two bytes, and this document does not say "only a few bytes" without saying
which and why.

**What would close it, and what it costs:** both machines holding the identical `AdvAPI32.Lib`.
That means vendoring the import library, or building in a pinned container image, or publishing
the runner's build as the official artefact and reproducing *that* on any runner of the same
image. The last is free and is the recommendation; it is a decision about what "the build" is, so
it is the owner's, not this session's.

### Where reproducibility stands

| claim | before | now |
|---|---|---|
| two builds, one machine, executable | identical | identical |
| two builds, one machine, installer | identical *by luck* | identical **by construction**, gated |
| two builds, one runner, installer | **differed** | identical, gated, verified on the runner |
| runner vs developer machine, executable | 3 205 190 bytes | **70 bytes, each accounted for** |
| runner vs developer machine, code | 199 608 bytes | **0** |
| runner vs developer machine, sizes | 9 858 560 / 9 854 464 | **identical** |

## 3. B5: the purpose checks, where they are decided and through the interface

Two halves, because the blocker had two.

### 3.1 Tested where they are decided

The four folder purposes and the file purpose were tested thoroughly — through their *helpers*.
`folder_chosen_for` had the full 4×4 matrix. The commands that pin the purpose had nothing, because
they take `tauri::State` and no test could build one.

The consequence, which is the part that matters: **changing `FolderPurpose::PublishInto` to
`ImportFrom` at the `prepare_publication` call site broke no test in the repository.** The property
was asserted where it was easy to assert, not where it was decided.

15 tests now drive the real commands through a `tauri::test` mock app, and the mutation table is
the evidence that they are worth having:

| mutation | tests that fail |
|---|---|
| `PublishInto` → `ImportFrom` in `prepare_publication` | 3 |
| `ImportFrom` → `PublishInto` in `chosen_publication_folder` | 4 |
| `GrantToComponent` → `ImportFrom` in `grant_set` | 5 |
| the record check in `input_file_chosen` replaced with `if false` | 6 |

One existing test was vacuous: it hand-wrote a `match` re-deriving `ImportError::FolderNotChosen`
instead of calling the function that pins the purpose. It now calls it, and the second mutation is
what proves that changed anything.

`start_workflow`, `choose_folder` and `choose_file` take `AppHandle<Wry>` and cannot be reached
from a mock runtime. That is written in the source rather than replaced with a helper test that
would look like coverage: `start_workflow` reaches the record through the same two calls
`run_graph` makes, and those are driven.

### 3.2 The machine, which turned out to exist

B5 said this needed "a machine where nobody is working", and the project had none: Windows 11
Home, no Hyper-V, no Sandbox, no Docker, and a person at the keyboard.

**The hosted runner is that machine.** `.github/workflows/gui-journeys.yml` builds, installs and
drives the application there, and UI Automation reaches both the WebView2 tree and the native
dialog. Established on the first run and not in doubt since: the window is found, the sidebar is
exposed, buttons are invoked, the chooser opens, and `install_check.ps1` passes 9 of 9 with the
installed binary's build stamp matching the commit.

### 3.3 What the runs found, including in the harness itself

**Run 1 — 15 passed, 14 failed, and one of the passes was false.** `ConfirmChooser` both printed
its report line and returned a bool; PowerShell collects printed output into the caller's
variable, so the result was a two-element array, and an array of two is truthy. That is how
`chooser closed on confirm -> dialogs left: 1` passed *while the dialog was still open* — and
every journey after it then found that stale dialog instead of its own. One vacuous assertion in
the harness accounted for most of the fourteen failures. The same class of defect this cycle was
sent to find in the product was sitting in the instrument.

**Run 2 — 24 passed, 8 failed, 3 skipped.** The chooser is now driven end to end: opened,
cancelled, the name field found by control id (`GetDlgItem(1152)` — it is not a direct child of
the dialog on Server 2025, which is why the first attempt could not find it), the path written and
**read back and compared before confirm is pressed**, and the dialog closed with none left.

Two of that run's failures were the application being right and the harness asserting wrongly, and
they are worth recording as evidence rather than as defects:

- the runner's `TEMP` is the 8.3 short form, and the folder came back as
  `C:\Users\runneradmin\...` rather than `C:\Users\RUNNER~1\...` — **the canonicalisation that
  every purpose check depends on, observed through the real chooser**;
- a junction came back as **its target**, not the link — which is exactly what
  `resolve_grant_directory` is supposed to do, proven through the GUI for the first time.

Both assertions compared raw strings. They compare paths as paths now.

**Run 3 — 41 passed, 2 failed, 3 skipped. Two purposes closed through the interface:**

- **`projects-location`**: opened, cancelled with the preference untouched, confirmed, and the
  folder became the preference. A junction came back as **its target**, not the link.
- **`import-from`**: opened, cancelled taking nothing in and opening no panel, then two negatives —
  a path that is not there was refused by the shell (*"Path does not exist."*), and a junction was
  resolved to its target, whose contents the application then refused in its own words: *"There is
  no publication.json in that folder, so nothing in it says what it is. That is a folder of files,
  not a publication."* Translated, specific, and shown to the person.

**Run 4 — 38 passed, 6 failed, 3 skipped, and the regression is the point.** Run 3's
`a step is on the canvas` was the fourth vacuous assertion: it matched the text of the palette
button it had just pressed. Replaced with one that requires a real `node-*` id to appear, it fails
— so **no step has ever reached the canvas in any run**, and journeys 2, 4 and 5 have never been
reachable. Three runs' worth of apparent progress on them was an artefact of that one check.

That is the honest state of B5 at the time of writing: **two of the five purposes driven end to
end with their negatives; three not driven at all.** The obstacle is understood and is in the
harness, not the product — the palette item is a real `<button>` whose `onClick` calls `addNode`
(`Palette.tsx:36-48`), the manifest map is keyed exactly as the palette spells the reference
(`store.ts:319` against `store.ts:329`, both `id@version`), a placed node renders
`id={`node-${id}`}` (`ComponentNode.tsx:131`), and the Inspector was observed in its *empty*
state, which means nothing was selected, which means `addNode` never ran. So the activation does
not reach React, and the next run reports the button's supported patterns and tries three ways of
pressing it.

Also recorded from run 4, for whoever picks this up: the Save As dialog exposes
`Pane 'File name:'` with a real window handle and **no Edit at all** — `edit windows=[]` — which
is why writing the path by any Edit-shaped route fails there while it works for the folder picker.

**Run 5 — 41 passed, 4 failed, 3 skipped. The question is now answered, and the answer is not
what was assumed.** The run was built to settle why no step reaches the canvas, and it did:

- The palette is **not** empty: it offers **21 components**, each with its reference in the help
  text (`encastra.data.json@1.0.0`, `encastra.file.save@1.0.0`, …). The manifest map is loaded, so
  the silent `if (!manifest) return;` in `addNode` is not the cause.
- The palette item is a **proper button**: `type=Button enabled=True offscreen=False
  keyboardFocusable=True rect=(96,175 196x54) patterns=Invoke+ScrollItem`. Nothing is covering it —
  the accessibility layer, asked what element sits at the item's own centre, names that same item.
- It was activated by **all three routes** — UIA `Invoke`, MSAA `accDoDefaultAction`, and focus
  plus Enter and Space — and **neither witness ever answered**: no `node-*` id appeared anywhere
  on screen, and the Inspector never showed the reference. The Inspector stayed on
  *"Select a step to configure it, or pick a component to begin."*

So the button is real, reachable, enabled and pressed, and no step is placed. `Palette.tsx:45-47`
states the intent this contradicts, in a comment written deliberately:

> Dragging is the natural gesture, but everything on this canvas must also be reachable
> from the keyboard, so activating the button places the node too.

**There is no test of that promise anywhere.** Nothing in `apps/desktop/test/` asserts `addNode`,
and the repository has no DOM test environment, so the path from the button to the store has never
been exercised by anything but a person with a mouse. That is the gap this cycle actually found,
and it is larger than the harness bug it was looking for.

Two readings remain open and this session cannot choose between them from here: either activating
the palette button genuinely does not place a step — an accessibility defect in the product, since
the keyboard is the route the comment promises — or React Flow does not place a node under the
runner's display in a way the accessibility tree can see. **What settles it is a rendered-DOM test
of `PaletteItem` asserting `addNode` is called, which the repository cannot currently run.** That
is the next piece of work, and it is worth more than another harness revision: it would cover a
promise made in a comment and kept by nothing.

### 3.4 Four assertions that passed for the wrong reason, three of them in the instrument

This cycle was asked to hunt for tests that pass without exercising what they claim. Four turned
up. One was in the product's suite. **Three were in the thing built to test it** — worth writing
down, because a harness is exactly where nobody goes looking:

| where | the assertion | why it passed |
|---|---|---|
| `lib.rs` tests | a folder chosen to publish into is not one to import from | hand-wrote a `match` re-deriving the error instead of calling the function that pins the purpose |
| harness | `chooser closed on confirm` | the function both printed its report line and returned a bool; PowerShell made that a two-element array, and an array of two is truthy — so it passed while printing `dialogs left: 1` |
| harness | `the path is in the chooser before it is confirmed` | checked *what* was in the control, not *which* control — the path was in the Save As dialog's Search Box |
| harness | `a step is on the canvas` | matched the text of the palette button it had just pressed |

The shape is the same every time, and it is not carelessness: each checks something adjacent to
the property and correlated with it — the error type rather than the code path, the text rather
than the control, the button rather than its effect. Each is invisible until somebody asks what it
would take for this to pass while the thing is broken, and that question has to be answered by
running it. Which is what the mutation tables in §3.1 are.

## 4. Things found on the way that were not on the list

**Secret scanning has never run on a pull request.** `gitleaks-action` asks the API for the pull
request's commits; with only `contents: read` that returned 403 and the action threw. The job went
red identically for a clean branch and for one carrying a key. All six open Dependabot pull
requests are red for this and not for their contents —
`docs/audits/2026-09-16-dependabot.md` reads each one.

**A refused folder did nothing at all.** Four of the five chooser call sites awaited the promise
outside any catch, so a refusal from the runtime produced an unhandled rejection and no message.
Fixed, with a test pair per call site: a refusal must show, a cancel must not.

**`release_check` called an unfinished CI run a failure.** An in-flight run has no conclusion, and
`conclusion != "success"` read that as broken — so the verdict depended on when it was asked.

**`encastra-wt-rc/target` is a junction to `encastra-wt-build2/target`.** Those two worktrees have
never been independent builds; any claim resting on them agreeing rests on one directory agreeing
with itself. No published claim depends on it — `reproduce.py` builds in fresh worktrees under
`%TEMP%` — but it is a trap worth removing.

**A stale executable in a worktree's `target/`** was caught by `release_identity.py` during this
work, which is the check doing its job.

## 5. B5: what was actually wrong, what is fixed, and what is still open

§3 left B5 with an honest unknown: two of the five purposes driven end to end, three not driven at
all, a palette button pressed three ways placing nothing, and no way from there to tell a product
defect from a blind harness. This section answers that question, and finds more than it asked
about. The step that was never placed was the harness's blindness, not the product. Two defects
did turn up in the product on the way, §5.3 and §5.7.1, and both are fixed.

### 5.1 Four purposes or five

The contract is **five**: four folder purposes — `projects-location`, `publish-into`, `import-from`,
`grant-to-component` — and one file purpose, `run-input`, served by `choose_file`, which was added
in the `rc/consent` wave. `RELEASE_CANDIDATE_READINESS.md` §7 says "four native chooser flows"
because it was written before the file chooser counted as one of them; the sentence beside it in
the same row already names "the new file chooser" separately. Both instruments now say five and
name them with their call sites: `scripts/verify/gui_journeys.ps1:8-16` and the `gui.journeys`
docstring in `scripts/release_check.py`.

### 5.2 The chain, and where each half broke

    palette button → onClick → addNode → store → React Flow → rendered node → observable in the GUI

Measured with the DevTools protocol against the built application (`scratchpad/opusB/`):

- **The activation works, and always did.** A DOM click, a real mouse press, a real `Enter` and a
  real `Space` each place a node. `forensic-log.txt:114-136` — `E1 AFTER (poll<=3000ms): { "hit":
  true, "elapsedMs": 12 … "nodeIdList": ["node-json-1"] }`, with the mutation observer timing it at
  `"deltaMs": 7.7`. The four gestures measured 7.7, 7.4, 5.8 and 6.1 ms.
- **The accessibility tree cannot see the result.** `forensic-log.txt:365` — `E4 AX tree total
  nodes: 395` — and `E4 AX nodes whose serialization mentions "node-": 0 []`. The placed node comes
  through as `role=generic name="" ignored=false props=[]`, and so does its React Flow wrapper,
  whose only identity is in attributes (`e11-log.txt`: `data-id`, `data-testid rf__node-json-1`,
  `aria-roledescription node`). So the harness's step oracle — a search for an `AutomationId`
  containing `node-` — was a **permanent false negative**. That is the first defect, and it is
  ours: HARNESS / TEST_OBSERVABILITY, not a product regression.
- **A second trap sat behind it.** `onlyRenderVisibleElements` (`Canvas.tsx:826`) removes off-screen
  nodes from the DOM, and `addNode` places each new node at `rightmost.x + 260` (`store.ts:348`) on
  a 648 px canvas. From the third press on, the node is added to the DOM and taken straight back
  out: `e10-log.txt` — `CLICK #3 … ids=["node-json-1","node-json-2"] … mutations: added
  ["node-json-3"] … removed ["node-json-3"]`, while the status bar reads `"6 pasos"`. After Fit View
  all six are in the DOM (`e11-log.txt`, `AFTER fitView: ids=[…six…] rf=6`). Any oracle that counts
  DOM nodes without fitting first will call a culled node a missing one.

### 5.3 The real product bug found on the way

While proving the node was placed, a separate defect turned up that no harness revision would have
found: **the Inspector never followed a palette add.** `e12-log.txt`, on the beta.1/rc.3 code, with
`node-json-1` selected by a real mouse click first:

    after palette add: {"inspTitle":"PARSE JSON", … "selectedRF":["json-1"],
                        "isSelectedCls":["node-json-1"], "ids":[… ,"node-save-7"]}

The new step is on the canvas and the selection did not move. Root cause: `addNode` named the new
node in `selectedNodeId` but built it without `selected` and left every other node's flag alone.
React Flow keeps its own selection; on the next render it fired `onSelectionChange` with the
selection it still held and `select()` put the store straight back. The fix (`879e5b4`,
`apps/desktop/src/store.ts:350-356`) gives the new node `selected: true` and writes every other node
unselected — which is what `pasteClipboard` already did. Classification: **REAL_PRODUCT_BUG**,
keyboard-reachability. It is the promise in `Palette.tsx:46-47` half-kept: the step was placed and
could not be reached.

Verified on the rebuilt binary (`scratchpad/audit/verify_fix.mjs`): after the click, the Inspector
reads `PARSE JSON / encastra.data.json@1.0.0`, `rfSelected ["json-1"]`, `domSelected
["node-json-1"]`; after a real `Enter` on the fourth palette item, `count 4` and the Inspector reads
`WRITE JSON`.

### 5.4 The DOM test layer, and the mutations

Nothing in this repository had ever rendered a component into a document. Two things were in the
way, and both were fixed in `c89bdde`: there was no DOM (jsdom, Testing Library and user-event added
at the root workspace, pinned, dev-only, `docs/THIRD-PARTY.md` unchanged), and `vitest.config.ts`'s
`include` globs matched only `*.test.ts` under `packages/*` — a rendering test, which must be a
`.tsx` file, would have been collected by nothing and reported as nothing. The global environment
stays `node`; the files that need a document ask with `// @vitest-environment jsdom`.

`apps/desktop/test/palette.test.tsx` (7 tests) presses the real button by mouse, `Enter` and
`Space`, and asserts the whole result — type, component reference, config defaults, position, id,
both halves of the selection, and the project reading as edited. `apps/desktop/test/add-node.test.ts`
(4 tests) asks the store the same question with a selection already on the canvas.

Those two files ask the store, and the defect in §5.3 was not in the store alone. It was the round
trip: React Flow reported its own selection back through `onSelectionChange` and undid the store's.
An adversarial review pointed out that no test rendered React Flow, so the mechanism of the bug was
untested. `apps/desktop/test/canvas-selection.test.tsx` (3 tests, `7fd154b`) renders the real
palette and the real canvas over the real store. It presses palette buttons, waits until React Flow
has drawn and measured the node, and then asks four things: the store's `selectedNodeId`, which
store nodes carry `selected`, which nodes carry React Flow's `.selected` class in the DOM, and the
last selection React Flow reported. The third case reproduces the defect's shape: React Flow already
holds a selection, made by clicking a node on the canvas, when the next palette press arrives. A
wrapper on `select` records every call, which proves that `onSelectionChange` actually ran in the
test rather than being assumed. jsdom has no layout, so the file stubs `ResizeObserver`,
`DOMMatrixReadOnly` and element sizes; without the sizes, `onlyRenderVisibleElements` culls every
node.

| mutation applied to product code | tests that fail |
|---|---|
| palette: delete the `onClick` | 4 |
| palette: make the state update return `{}` | 4 |
| palette: write the wrong node type (`'wrong'`) | 1 |
| palette: drop the node before it reaches the array | 4 |
| palette: move the handler to `onDoubleClick` | 4 |
| selection: drop `selected: true` on the new node | 5 in the store tests; 3 of 3 through React Flow (`expected null to be 'uppercase-1'`: React Flow reported an empty selection and the store was reset) |
| selection: stop deselecting the other nodes | 3 in the store tests; 2 of 3 through React Flow (`expected [ 'uppercase-4', 'count-5' ] to deeply equal [ 'uppercase-4' ]`: two nodes selected). The one that passes has no other node to deselect |

### 5.5 The oracle the harness uses now

After **one** activation, three independent questions asked of the page (`scripts/verify/cdp.mjs`,
`scripts/verify/gui_journeys.ps1`):

### 5.6 The runner, in four runs

| run | decisive line |
|---|---|
| 35058615026 | `FAIL CDP reachable -> {"error":"no CDP endpoint on 127.0.0.1:9222 (fetch failed)…"}` — one attempt, no wait, no diagnostics. The absence of a finding, not a finding. |
| 35060930065 | `note webview2: pid=7700 host=encastra-desktop.exe type=browser remote-debugging-port=absent`, with the variable provably set in the process that called `Start-Process`. So the flag is not a property of the application. |
| 35062783047 | `-Launch` cleared the machine and started the application itself: `pid=7156 parent=1268 host=encastra-desktop.exe type=browser remote-debugging-port=absent`. Parented to our own host, environment block written by us, still no flag. |
| 35064817460 | `note -Launch : this process is ELEVATED, so WebView2 ignores the environment variable and any HKCU policy; the override has to be under HKLM` → `PASS CDP reachable -> node … is talking to the page titled 'Encastra' on 127.0.0.1:9222, after 493 ms of waiting`. |

It is not a bug. From *Develop secure WebView2 apps*, under "For an elevated host app, use
appropriate override flags": when the host process is running elevated, `WEBVIEW2_*` environment
variable overrides are ignored, including `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`; HKCU policy
overrides are ignored; `AdditionalBrowserArguments` registry overrides under HKCU are ignored;
**HKLM policy overrides are honored.** A hosted runner is an administrator with UAC off, so every
host started there is High Integrity Level and the variable was never going to arrive.

So `-Launch` writes the documented override before it starts the application, named for this
application and never `*` — a wildcard would arm a debugging port in every WebView2 application on
the machine. Run 35064817460 ends with ten `note -Launch : removed …` lines, HKLM and HKCU, values
and the empty keys it created.

That was not enough, and the adversarial review showed it from this work's own evidence: run
35074744558 wrote the policy, was cancelled, and has no `removed` line at all. A trap does not run
when the process is killed. On a hosted runner the machine is thrown away with the job. On any
machine that is kept, every later launch of Encastra would open the debugging port. Since `9a59cf4`
the take-back no longer depends on the process living to its end:

- before writing, the harness records in a journal what it is about to write and what was there:
  each value's data and registry kind, and which keys existed. It writes the journal atomically,
  and only then writes the policy;
- every start of the harness, a new `-RemovePolicyOnly` mode and every normal end restore exactly
  what the journal recorded, with the original value kind. They delete only the values the run
  created, and only if they still hold what the run wrote. Every failure is a FAIL, and the journal
  is kept until the restore succeeds;
- the workflow runs `-RemovePolicyOnly` in an `if: always()` step and uploads its log;
- the cleanup runs before the SUMMARY line, so the summary counts it.

Checked locally, not elevated, so under HKCU: the harness process was killed mid-run, the value and
the journal were still there, and `-RemovePolicyOnly` removed the value, the key it had created and
the journal. Pre-existing `ExpandString` and `MultiString` values came back with their own kinds.
The HKLM path has only run on the runner.

### 5.7.1 A second product defect: two panels whose buttons could not be reached

The runner found this one, and it is not a harness problem: a person on a laptop screen could not

### 5.8 What was **not** verified

- The HKLM route has only ever been exercised **on the hosted runner**. Nothing here says it is the
  right mechanism on a developer machine, and on a non-elevated host the environment variable is
  what is honoured.
- **B7 is unchanged.** Nothing in this section touches the cross-machine reproducibility of the
  candidate's bytes.
- Nothing here says anything about macOS or Linux. There is no evidence for either.
- **UI Automation still cannot see a canvas node**, and this is ACCEPTED, not fixed. The node
  deliberately carries no ARIA role — `ComponentNode.tsx:124-131` says why, and the canvas's live
  region is what announces the selection. The consequence is that a UIA-only oracle cannot observe
  the canvas; the DevTools protocol is how the harness observes it instead.

- **The final run did not happen.** Everything committed after `c744ffb` — the j1 wait, the
  Publish-panel click path, the run-start wait in j4 and the panel fix — has been checked locally
  over CDP only. None of it has been through the runner, because the runner refused the job for
  billing.
- **A native chooser opened on the developer's desktop.** It happened once, for a few seconds,
  during the panel measurements. An attempt to answer the Import IPC by replacing
  `window.__TAURI_INTERNALS__.invoke` silently did nothing, because the property is not writable,
  so the real `choose_folder` ran. The probe killed its own process, and nothing was chosen or
  written. Every later measurement answered at `window.fetch` and checked first that the answer was
  in place. This is the reason the journeys run on a hosted runner and never on this machine.
- **What a fresh iteration means.** Under `-Launch`, each iteration after the first stops the
  application and starts it again, so the grants it holds in memory start empty. Only on CI does it
  also delete the application's per-user state first: preferences, `welcomeSeen` and the imported
  library. The delete refuses any folder that is not the application's own. Without `-Launch`, an
  iteration shares the process with the one before it and only gets a fresh project and sandbox.
  None of the restart path has run on the runner yet.
- **Cancel is checked once.** "Cancel leaves the preference unchanged" reads the value once after
  the dialog closes. A wrong write arriving later would not be caught.
- **The Import panel's other states were not measured** after the panel fix: the refusal, reading
  and writing states. Only the inspected state was opened. All heights except 820 were emulated.
