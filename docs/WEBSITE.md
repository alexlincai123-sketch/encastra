# Website

`apps/web` — what Encastra is, for somebody who has never seen it.

---

## 1. Why it exists

Until 0.2 the only way to find out what Encastra was, was to read the source. That is the gap
this closes. The site has one job before any other: a visitor should understand, in well under
a minute, that **you assemble software out of components rather than writing it from scratch**,
and should be able to watch that happen.

## 2. Stack

Next.js App Router, TypeScript, GSAP with ScrollTrigger. No CMS, no database, no authentication,
and no API route that does anything privileged. Static where it can be.

It shares the repository's tooling — Biome, the same TypeScript settings — and, more importantly,
the product's design tokens (`packages/ui/src/tokens.css`) and brand assets
(`packages/ui/brand/`). The site and the application are one product, so they take their colour,
spacing and type from one place rather than two that drift.

The site may be more expressive than the application: the desktop is for working in, the site is
for finding out. The vocabulary stays the same.

## 4. The interactive terminal

The centrepiece, and the thing most likely to be misunderstood, so it is worth being exact:

**It is an animation. It never evaluates anything.** No `eval`, no `new Function`, no
server-side execution, no input element, and no path by which a visitor's typing could reach
anything that runs. It replays a transcript held as data in `src/lib/terminal-script.ts`, with
play, pause, restart and speed controls.

That is a security boundary, not a stylistic choice. A terminal on a marketing page that really
executed commands would be a remote code execution feature with a friendly face.

What makes it teach rather than decorate: as each line is announced, the workflow diagram beside
it lights up the step being described. The terminal says what happened; the diagram shows where.
The transcript also runs the *refusal* before the success — a component asking for a folder
nobody allowed, being refused, and then being allowed — because that refusal is the product
working, and it is the single most important thing a visitor can understand about it.

Accessibility: the full transcript is exposed statically to screen readers, separate from the
animated view, and `prefers-reduced-motion` genuinely skips the animation rather than shortening
it.

## 5. What the site must never do

These are the rules the pages were written under, and the ones to check any change against.

- **Never present something unbuilt as working.** The marketplace, community, accounts,
  payments, the WebAssembly sandbox for third-party components and the update channel do not
  exist. They are labelled, visibly, and are not interactive.
- **No invented numbers.** No user counts, download counts, testimonials, reviews or ratings.
  The component count is generated from the real manifests; if a number cannot be derived, it is
  not shown.
- **Never claim the build is signed.** It is not, and the download page says so plainly next to
  the hash.
- **Never "100% secure".** Describe the model and its limits, and link to the real documents.
- **The legal documents are drafts.** Every one carries a prominent notice that it requires
  review by qualified counsel and is not legal advice.

## 6. Where the facts come from

Nothing on the site is retyped from memory.

- **Components**: generated from the real manifests by `scripts/generate-components.mjs` into
  `src/lib/components.data.ts`.
- **Types and conversions**: from `packages/protocol/data/type-graph.json`.
- **The release**: filename, size, SHA-256, commit and signing status in `src/config/site.ts`,
  taken from `docs/RELEASE.md`, which is itself generated by `scripts/release_manifest.py` from
  the artefacts. `RELEASE_MATCHES_VERSION` lets a page say so honestly when the published
  artefact is older than the version the site is at, rather than quietly implying they match.
- **The version**: one constant, from the single source enforced by `tests/version.test.ts`.

One correction worth recording, because it was wrong in three places at once: **Watch Folder
outputs `file`, not `image`.** `file → image` is an *explicit* conversion (`decode-image`, which
can fail), so the first edge of the sample workflow is not "IMAGE → IMAGE". The terminal
transcript, `/how-it-works`, `/templates` and `/tutorials` all describe it as the decode it
actually is.

## 7. Checks

```bash
npm run build --workspace @encastra/web
npx tsc --noEmit -p apps/web
npx biome check apps/web
```

All three run in CI, alongside the desktop build. `next-env.d.ts` is excluded from Biome: Next
regenerates it on every build in a shape Biome would reformat, and fighting a code generator in
every commit is worse than not lint-checking a two-line file the project does not own.

## 8. Not done

- **It is not deployed anywhere.** There is no host and `encastra.dev` is not registered; the
  URL exists only to build canonical links. Nothing about the site claims otherwise.
- **No analytics, and none planned without asking first.**
- **The download only offers Windows**, because that is the only installer that exists. macOS
  and Linux are stated as not built rather than offered as "coming soon" buttons that do
  nothing.
